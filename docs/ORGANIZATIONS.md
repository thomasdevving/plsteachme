# Organization training workspaces

Schools, training providers and businesses can create private AI-guided training modules, enroll students or employees, and monitor their progress at `/training`.

## Plans

Organization pricing is $100–$500 per month, by learner seats:

| Plan | Learner seats | Monthly |
| --- | --- | --- |
| `up-to-25` | 25 | $100 |
| `up-to-75` | 75 | $200 |
| `up-to-150` | 150 | $350 |
| `up-to-300` | 300 | $500 |

Invited and active learners use a seat; admins and instructors are included. The seat limit is enforced inside the database transaction. **Billing is not active**: choosing a plan sets the seat limit and no payment is taken. Above 300 learners, the workspace points to the existing pilot form. Plan definitions live in `lib/training-contract.ts` and in the `training_mutate` SQL function; keep both in sync.

## Setup

Run `supabase/migrations/20261019120000_organization_training.sql` after the earlier migrations. It creates the `training_*` tables (RLS on, no browser access), the service-only `training_mutate` function, and the private `organization-training` Storage bucket. It uses the same `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, Supabase Auth and `OPENAI_*` settings as the teacher platform (see `PLATFORM.md`).

Optional: set `TRAINING_CREATOR_IDS` to a comma-separated list of Supabase Auth user IDs to limit who can create organizations during a pilot. When it is empty, any signed-in account can create one. AI generation and coaching share the per-process rate limits of the teacher platform; set provider spend limits before opening creation widely.

## Roles

- **Admin**: everything below, plus inviting and removing people, changing roles, choosing the plan, publishing, assigning and archiving modules. An organization always keeps at least one active admin.
- **Instructor**: creates and edits modules, generates drafts with AI, and sees people and progress.
- **Learner**: practices published modules assigned to them.

## Enrollment

Admins paste up to 100 email addresses at a time and choose a role. The server returns one personal link per address, once; only a SHA-256 hash of each token is stored. Links expire after 30 days. A link can only be accepted by a signed-in account whose verified email matches the invitation, so a forwarded link is useless to anyone else. No email is sent by the app: admins share the links themselves (copy or CSV). Removing a member keeps their progress records for reporting and frees the seat.

## Creating modules

Each module starts private as a draft from one of three sources; all can be combined.

1. **Demonstration with camera tracking.** The admin records themself performing the skill in the browser (or loads an existing video). MediaPipe hand tracking runs on the device (`lib/vision/demonstration-tracking.ts`): when the hands have been working and then hold still, a still is captured as a candidate step result. *Mark step* captures a moment manually. Nothing leaves the device until the admin saves the moments (up to 12), adds captions and optionally uploads the recording for learners. The server re-encodes each still (resized, metadata stripped) into the private bucket. Steps can be built one-per-moment without AI, or generated by AI, which maps each step to its best moment. Narration from an uploaded MP4/WebM under 25 MB can be transcribed after separate consent.
2. **Manual.** Upload a PDF (up to 20 MB) or load a text/Markdown file, optionally naming a focus section. The PDF goes to OpenAI as a file input only when the admin requests generation with consent.
3. **Written.** Start blank and write every step.

AI output is a draft: it keeps the module's title and category, flags facts to verify, and is never saved or published automatically. Each step can carry an *instructor reference still*. Publishing requires the same checkpoint completeness as teacher lessons, an explicit review confirmation, and an admin. Each publication creates an immutable version; editing a published module does not change what learners see until it is published again.

## Practice and progress

Learners see assigned modules, the instructor reference still for each step, and the optional recording. Camera coaching uses the shared coach UI, authorized per check by organization membership rather than the one free trial. When a step has a reference still, it is sent alongside the learner frames so the model can compare the result with the instructor's. Non-visual steps never verify; low confidence becomes *unclear*.

Progress is saved to the organization per learner, module and version. **Camera confirmations are recorded only by the server** after a high-confidence match; a browser claim of a camera-confirmed step is downgraded to a self-check. The first completion is kept even if the learner practices again. Publishing a new version starts fresh records. Admins and instructors see completion, camera-confirmed, self-checked and open checkpoints per learner, and can export CSV. Neither signal certifies competence or safety.
